# TinyInfer Workflow Authoring Standard

> 版本：v1.0
> 制定日期：2026-07-22
> 适用范围：所有交给 agent 执行的 TinyInfer 工作流

## 1. Objective

本文件规定了为 TinyInfer 项目编写工作流文档时必须遵循的结构和质量要求。遵守此标准的文档可供
agent 严格按照步骤执行并留下可审计的证据，不依赖人工记忆或口头约定。

## 2. Mandatory Sections

每个面向 agent 执行的工作流文档必须包含以下 **16 个部分**。任何工作流缺少其中一项即被视为
不完整，必须在执行前修补。

### 2.1 Objective（目标）

明确回答"这份工作最终改变什么"。一句话说明该工作流完成后仓库或环境将处于什么状态。

### 2.2 Non-goals（非目标）

列出工作流执行过程中**明确禁止顺手加入**的内容。这防止 scope creep，确保 agent 不会在实施
A 时意外引入 B。

### 2.3 Preconditions（前置条件）

执行开始前必须成立的环境、分支、依赖和权限。至少覆盖：

- 操作系统与发行版。
- Python 版本。
- 需要的系统工具（如 git、uv）。
- 网络可达性（GitHub、PyPI、Hugging Face 等）。
- 文件系统路径和可用空间。
- Git 分支和远端状态。

### 2.4 Baseline Evidence（基线证据）

开始前运行哪些命令并保存什么结果。这些证据用于确认执行前的状态是可解释的，并在出现问题时
提供对比基准。

### 2.5 Artifact Manifest（产物清单）

列出工作流将创建、修改、生成和**禁止提交**的文件。对每个文件注明其类型（代码/测试/文档/
快照/配置）和变动方式（新增/修改/重命名/删除）。

### 2.6 Detailed Workflow（详细工作流）

严格编号的执行顺序。每一步必须有唯一编号，并引用对应的 Task 定义。步骤之间不允许隐含依赖，
必须显式声明每步的输入和输出。

### 2.7 Per-task Inputs / Actions / Outputs（任务三要素）

每个 Task 必须包含三个明确小节：

- **Inputs**：开始该任务前必须存在的文件、环境变量、运行中的服务或前置任务输出。
- **Actions**：具体的命令、代码变更或手动操作。
- **Outputs**：任务完成后可检查的产物（文件、退出码、终端输出行等）。

### 2.8 Acceptance Criteria（验收标准）

每个 Task 的可观察通过条件。使用明确的可测量条件，例如：

- 退出码为 0。
- 特定文件存在且包含特定内容。
- 某行输出匹配正则表达式。
- 测试数量 ≥ N。

禁止仅使用"完成"、"通过"等主观描述。

### 2.9 Gate / Exit Criteria（关卡/退出门）

定义允许进入下一阶段（或下一工作流）的证据集合。每个 Gate 至少包含：

- 需要通过的验证命令及其预期退出码。
- 需要存在的文件清单。
- 需要满足的 Git 状态条件。
- 禁止存在的错误状态（如 dirty worktree）。

### 2.10 Definition of Done（完成定义）

代码、测试、文档、Git 和交付物的完整完成定义。按维度列出：

- **功能**：代码按设计工作。
- **正确性**：测试全部通过。
- **工程质量**：lint、format、typing 通过。
- **文档**：所有相关文档已更新且一致。
- **安全**：无敏感信息泄露。
- **可复现**：命令、版本、硬件已记录。
- **版本控制**：改动已提交并审查。
- **发布**：标签指向正确提交。
- **边界**：后续阶段未被误标为完成。

### 2.11 Verification Commands（验证命令）

可复制命令与预期退出码/关键输出。命令格式为纯文本，可直接粘贴执行。每个命令附带：

- 工作目录。
- 预期退出码。
- 关键输出行或正则匹配。
- 运行环境要求（如"需要 GPU"）。

### 2.12 Stop Conditions（停止条件）

遇到哪些情况必须停止而不是猜测或跳过。例如：

- 网络不可达。
- 依赖版本不匹配。
- GPU 不可用。
- lock file 不一致。
- 测试失败。
- 出现未预期的 Git 状态。

### 2.13 Failure Handling（失败处理）

失败证据的收集方式、清理步骤和恢复方式。至少包含：

- 如何收集失败日志。
- 是否需要回滚文件变更。
- 是否需要恢复 stash。
- 哪些错误可重试，哪些必须人工介入。

### 2.14 Git / Worktree Rules（Git 与工作树规则）

基线、分支、提交边界、合并和标签规则。明确：

- 在哪个分支上工作。
- 使用 worktree 还是直接 checkout。
- 提交消息格式约定。
- 合并策略（fast-forward / merge commit / squash）。
- 标签命名规则和类型（annotated / lightweight）。
- 是否允许强推。

### 2.15 Agent Handoff Contract（Agent 交接契约）

Agent 开始前必须阅读什么、结束时必须报告什么。

**开始前必须报告：**
- 当前分支名和 HEAD SHA。
- origin/main SHA。
- worktree 路径。
- dirty files 清单。
- 已确认未将当前门误标为后续阶段。

**结束时必须报告：**
- 修改或新增的每个文件（含路径和变动类型）。
- 实际运行的每条验证命令及其退出码。
- 通过数量、失败数量和关键输出。
- 与每个 Acceptance Criteria 的对应关系。
- 仍未完成或被阻塞的事项。
- 当前 Git status 和最终 commit SHA。

Agent 不得根据旧报告、截图或另一 agent 的口头结论直接勾选 Gate。完成声明必须来自当前提交
上的新鲜验证证据。

### 2.16 Status Vocabulary（状态词汇）

| 状态 | 精确定义 |
|------|----------|
| `not started` | 前置条件尚未确认，或没有任何可观察的进展。 |
| `in progress` | 至少一个 Task 的 Actions 已开始执行但 Acceptance Criteria 未全部满足。 |
| `blocked` | 遇到 Stop Condition 或外部依赖不满足，无法继续。必须附带 block 原因。 |
| `verified` | 所有 Acceptance Criteria 已逐条通过，所有 Gate 命令在当前提交上退出码为 0，证据为新鲜生成。 |

## 3. Prohibited Practices

以下做法在本项目中禁止：

1. **仅用勾选框作为验收证据**。勾选框可辅助阅读，但每个完成声明必须对应命令、退出码、
   测试数量、产物路径或可检查的 Git revision。
2. **用"已完成"三个字代替 Gate 检查**。
3. **根据旧报告或截图跳过当前验证**。
4. **把预计值写成实测值**。报告中的版本号、文件数量、测试数量必须来自当前环境命令输出。
5. **在报告中把自己写的代码路径当作事实而不重新生成快照**。
6. **混用 capability inspection 和 correctness test 的概念**。两者是独立证据源。

## 4. Template

使用 `docs/templates/WORKFLOW_TEMPLATE.md` 作为新工作流的起点。
